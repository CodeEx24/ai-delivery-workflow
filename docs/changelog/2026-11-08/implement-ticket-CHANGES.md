# implement-ticket — what changed

The skill now does only the **build** half of the delivery workflow
(`~/.claude/workflows/ai-delivery-workflow.md`, stage 4). It stops at a draft PR and hands
off. Judging the work moved to the review and test loop (gate → testers → reviewers →
approver → explainer), run by `/deliver` or started by hand. The skill went from 12 phases
to 9.

## Section by section

**Description (how the skill triggers).** Rewritten for the new scope: build to a draft PR,
ticket types, resuming after review verdicts, running as a dispatched worker. Added trigger
phrases: "fix this bug ticket", "run the spike", "address the review verdicts".

**Human checkpoints.** Still two, but different ones:
1. Owner decisions (questions with a recommendation first). Low-risk tickets with no real
   design choice may skip the questions.
2. Owner accepts the ticket record before code, for medium and high risk.
The old "stop before push" checkpoint is gone. The workflow has the builder push and open a
**draft** PR itself; merging is never part of this skill.

**Learn the project first.** Kept. Now also looks for the checks script and for how owner
guides are written. Kept the rule that the repo's own workflow doc wins over the skill.

**Phase 1 — Intake.** New: reads the ticket **type** (Feature, Bug, Chore, Spike) and adapts.
A table in SKILL.md shows the differences, with detail in the new
`references/ticket-types.md`. Bug: reproduce with a failing test first, record the root cause
in the ticket record and the PR, smallest fix. Chore: short record and proof of no behaviour
change. Spike: time-boxed, findings and recommendation in the record, never merged as
product code, follow-up tickets proposed. Branch and commit prefixes follow the type. The
risk list now matches the workflow's high-risk areas.

**Phases 2–3 — Explore and ask.** Kept as they were (file map, assumptions list, at most ~4
questions with a recommendation first). Bugs only get questions when the expected behaviour
is unclear.

**Phase 4 — Ticket record.** The intent / spec / plan / verification files are replaced by
**one** record, `docs/tickets/<KEY>-<n>.md`. It has a mandatory links block at the top
(ticket, every PR, related tickets). Large high-risk tickets get a folder instead. Owner
setup steps become `docs/actions/<name>.md` guides with front matter (status, tickets, order,
estimate). The owner to-do list is regenerated by the project's script and never edited by
hand.

**Phase 5 — Plan.** Now goes to the gitignored working folder
`.delivery/jobs/<KEY>-<n>/plan.md`. It is not committed.

**Phase 6 — Build.** Kept. Added: per-type rules, and helper agents with disjoint file
ownership (they run no git commands).

**Phase 7 — Checks.** Runs the project's checks script (default `scripts/workflow/checks`),
or the gate commands from the repo's docs and CI if there is no script. Never edit the
checks script to make a branch pass. The old full self-review is now a **quick self-check**:
read your own diff for leftovers.

**Phase 8 — Draft PR.** Commit, push, open a draft PR. Its description covers what was built,
the main files, the decisions and how to test; this replaces a separate build note. The PR
link goes into the record's links block (in its own commit), and the ticket moves to In
Review.

**Phase 9 — Hand off.** Writes `.delivery/jobs/<KEY>-<n>/job.json` (stage `built`, round 1)
and stops with a one-line report. `references/review-loop.md` explains how to run the loop
by hand with the eight agents and the risk routing table.

**New: resuming with CHANGES.** Reads the round's verdict files and fixes only what they ask.
Then re-runs the checks, pushes and bumps the round. At most 2 extra rounds; if round 3
still asks for changes, the ticket is escalated to the owner.

**Running as an Orca worker.** Updated. The brief is still the contract. Design questions now
go through the orchestration `ask` (the coordinator relays them). The worker now goes as far
as the draft PR and stops **before merge**; before, it stopped before push. It finishes with
a structured `worker_done` report.

## Removed (the review loop owns these now)

- Independent reviewer and security pass (old Phase 8): now reviewer-code and
  reviewer-security.
- Acceptance-criteria validation (old Phase 9): now tester-functional and the approver.
- E2E / browser walkthrough (old Phase 10) and **`references/e2e-walkthrough.md` (deleted)**:
  now tester-device. Its per-surface checklist is useful material for the tester-device
  agent file.
- The verification record (old Phase 11): evidence now goes to the ticket and the PR.
- Waiting for CI to turn green before calling the ticket done: the gate and `/merge-ticket`
  cover this. The builder still fixes a red CI run caused by its own push.

## Open questions

1. **`job.json` format.** The workflow doesn't define one, so the skill proposes a default
   (ticket, type, risk, stage, round, branch, PR, routing flags) and defers to whatever
   `/deliver` defines. Align the two when `/deliver` is written.
2. **Checks script in builder mode.** The workflow says the script writes
   `round-N/checks.md`. The skill tells the builder not to overwrite the loop's round files.
   It would be cleaner if the script had a local mode (no report file).
3. **Spike records.** A spike is never merged as product code, so its record would never
   reach the main branch. The skill suggests landing the record as a docs-only change and
   asking the owner when the repo's workflow doc is silent. Confirm that's what you want.
4. **Projects on the old layout** (intent / spec / plan / verification folders). They keep
   that layout, because the repo's workflow doc wins. Change it per project when you're
   ready to switch.

## Alignment pass (after all drafts were written)

- Open questions 1 and 2 are **settled**. `job.json` now uses the one schema in the `deliver`
  skill's `references/state-files.md` (`deliver-job/1`); `references/review-loop.md` lists the
  fields the builder fills and no longer proposes its own default. The hand-off stage is
  `built` (was `review`).
- The checks script has a local mode: without `--report` it only prints; the gate passes
  `--report round-N/checks.md`. Phase 7 and `references/verify-gates.md` say so.
- The manual loop follows the new round order: gate → testers → reviewers on the final commit
  → approver → explainer. A tester-device `BLOCKED` is never the builder's to fix.
- Owner-guide front matter uses `status: open | done` (same as wave-status and /deliver).

## Follow-up pass

- **Bug flow uses `test-driven-development`** (obra, installed globally) for reproduce-first:
  Phase 6 and `references/ticket-types.md` point at it (red for the reported reason before any
  fix, green on the full suite, refactor only after green; its `writing-good-tests.md` rules).
  Taken from `test-driven-development`: "watch it fail", "full suite, not just your file",
  "name the production change that would make the test fail".
- **Local backlog:** intake reads the ticket from `docs/tickets/backlog.md` and writes nothing
  to it (status derived from the branch and PR; comments on the PR). Notes in Phase 1 and
  `references/pr-and-ticket.md` section 6.
